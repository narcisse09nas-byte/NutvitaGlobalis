# Degree Programs — Lot 3: Admissions and students

## Objective

Lot 3 implements the admission workflow and the institutional student record. Authentication profiles and student records remain distinct: a profile is an identity, while `academic_students` is the authoritative academic file.

## Registers

- `academic_applications`
- `academic_application_documents`
- `academic_application_reviews`
- `academic_students`
- `academic_student_status_history`

Identifiers are generated by PostgreSQL:

- applications: `APP-YYYY-######`
- students: `STD-YYYY-######`

## Application workflow

`DRAFT → SUBMITTED → UNDER_REVIEW / INCOMPLETE → ELIGIBLE / WAITLISTED → ADMITTED / REJECTED`

Every transition requires a comment and is appended to `academic_application_reviews`. Admission decisions require `application.decide`; hiding a button is not the security boundary.

An admitted application can be materialized into one student record only. The operation selects the approved program version when the application does not explicitly identify one.

## Documents

Application files use the private `academic-documents` Supabase Storage bucket. The object path starts with the application UUID. Storage RLS and register RLS both protect access. The register stores document type, path, original filename, MIME type, size and verification history.

## Institutional interfaces

- `/degree-programs/admissions`: searchable and filterable application registry with controlled CSV export.
- `/degree-programs/admissions/[applicationId]`: application details, workflow, documents and review history.
- `/degree-programs/students`: searchable student registry with program/status filters and controlled export.
- `/degree-programs/students/[studentId]`: student 360° record and status history.

Course registrations, fees and earned-credit calculations are intentionally reserved for Lots 4 and 7. Their tabs already have stable locations in the student 360° file; no fabricated aggregate is stored in the student table.
